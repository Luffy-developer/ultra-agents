# 第 4 课：工具调用（Function Calling）

> **学完你能**：说清楚工具调用的完整流程；看出一个工具的说明书写得好不好；写出一个出错时也不会让 Agent 卡住的工具。

## 基础

### 1. 模型自己不能做事，只能「下单」
- 模型只会输出文字。它能做的，是**说出"我想调用哪个工具、参数是什么"**，由我们的代码去真正执行。
- 比喻：模型是餐厅经理，工具是后厨。经理不亲自炒菜，只下单："来一份宫保鸡丁"。后厨做好端上来，经理再端给顾客。

### 2. 完整流程（4 步）
1. 我们把**工具说明书**（名字、用途、参数）通过 `tools` 参数发给模型
2. 模型的回复里出现 `tool_calls`：「请帮我调用 get_weather，参数 `{"city": "北京"}`」。注意参数是一段 **JSON 文本**，要我们自己解析
3. 我们的代码执行这个函数，把结果以 `role: "tool"` 的消息发回给模型，并带上这次调用的 `tool_call_id`（模型一次可能调好几个工具，靠 id 对上号）
4. 模型看到结果后，组织成自然语言回答用户；也可能觉得还不够，再调用别的工具（这就是下一课的 Agent 循环）

说明书长这样：
```json
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询某个城市的天气预报。用户问到天气、要不要带伞时使用",
    "parameters": {
      "type": "object",
      "properties": { "city": { "type": "string", "description": "城市名，如：北京" } },
      "required": ["city"]
    }
  }
}
```

### 3. 工具的三种类型（来自 OpenAI 的 Agent 搭建指南）
- **查数据**：读信息，不改变任何东西。如查天气、搜网页、读文件
- **做动作**：会改变外面的世界。如发邮件、写文件、下单退款——这类要格外小心，往往要先问人
- **调度别的 Agent**：把另一个 Agent 当成工具来用（「多 Agent」那一课的子 Agent 就是这样）

### 4. 说明书怎么写：站在模型的角度
模型完全靠说明书来决定用不用、怎么用这个工具。Anthropic 的经验：
- **像给新同事写交接文档**：写清楚做什么、什么时候用、参数是什么意思、有什么限制。新同事看不懂的，模型也看不懂
- **人都选不准，模型也选不准**：如果两个工具的说明你自己读完都分不清该用哪个，模型一定会选错
- **防呆设计**：让工具很难被用错。Anthropic 做编程 Agent 时发现，模型换了目录后总把相对路径写错；把工具改成必须填绝对路径，这类错误就没了。他们花在改工具上的时间，比改整体 Prompt 还多

### 5. 出错时：返回一段「怎么改」的说明，而不是让程序崩掉
- 模型传错参数是常事。工具出错时，**把错误写成一段说明交回给模型**，模型下一步就能自己改正
- 好的错误说明要讲清：**错在哪 + 正确的写法是什么**。比如"查不到火星的天气，支持的城市：北京、上海、广州"，而不只是"错误 404"
- 看看本项目：`src/tools.ts` 里 `edit_file` 找不到要改的文字时，返回"文件里找不到 old_string。先用 read_file 看看文件现在的内容，空格、缩进、换行都要一模一样"——这就是写给模型看的错误说明

### 6. Hooks：每次都必须发生的事，不能靠模型自觉
工具是模型决定要不要调用的，但有些事你希望**每次都必须发生**。这时用 **Hooks**（钩子）：在特定的时刻，**程序**自动运行你写好的命令，不经过模型。
- 本项目支持 4 个时刻：工具调用前（`PreToolUse`）、工具调用后（`PostToolUse`）、你发消息后（`UserPromptSubmit`）、导师回答完（`Stop`）
- 例子：导师每写完一个文件就自动格式化；导师想运行带 `rm -rf` 的命令时直接拦下（命令以退出码 2 结束 = 拦下）
- 在 `~/.agent-tutor/hooks.json` 里设置，输入 `/hooks` 查看写法。Claude Code 的 Hooks 也是这个原理
- 和 System Prompt 里写"不许删文件"相比，hook 是**写死在程序里的规则**，模型怎么说都绕不过去

## 进阶

### 1. Anthropic 的五条工具设计原则
1. **不要把 API 一个个照搬成工具，要合并成一个完整的操作**。比如安排会议，与其给模型「列出用户」「列出日程」「创建日程」三个工具，不如做一个 `schedule_event`；与其让模型 `read_logs` 读全部日志，不如给一个 `search_logs` 只返回相关的几行
2. **加前缀区分来源**：接了很多服务时，用 `asana_search`、`jira_search` 这样的名字，模型不容易混（本项目的 MCP 工具都以 `mcp__服务器名__` 开头，也是这个道理）
3. **返回有用的信息，而不是一堆编号**：用人能看懂的名字代替 UUID 之类的长 id。可以让模型自己选返回 `concise`（精简）还是 `detailed`（详细）——Anthropic 的 Slack 例子里，精简版只用了约 1/3 的 token
4. **控制返回的长度**：结果太长会撑爆上下文。要分页、过滤、截断，并告诉模型怎么拿到剩下的部分。Claude Code 默认把工具结果限制在 25,000 token；本项目的 `read_file` 超过 8000 字就截断，并提示"可以用 offset 和 limit 分段读取"
5. **参数名要一看就懂**：用 `user_id`，别用 `user`（是名字？是 id？还是整个用户对象？）

### 2. 工具多了，模型会选错——关键在「重叠」
- OpenAI 的经验：问题往往不在工具数量，而在**工具之间是否重叠**。有的系统 15 个以上说明清楚的工具也没问题，有的不到 10 个功能重叠的工具就经常选错
- 工具实在太多时，可以先按任务挑出相关的几个再交给模型（微软的课程建议一次不超过 30 个）

### 3. 工具也要评估、迭代
- 准备一批贴近真实的任务（如"客户 9182 被重复扣款三次，找出相关日志，看看有没有别的客户也受影响"），让 Agent 去做
- 除了看做没做对，还要看：调用了几次工具、用了多少 token、出了几次错
- 把 Agent 的运行记录拿出来读：它在哪一步选错了工具、传错了参数，就改那个工具的说明书或设计（「评估与上线」那一课会讲完整做法）

## 常见误区
- ❌ "模型自己执行了函数" → ✅ 模型只说出要调用什么、参数是什么，执行的永远是我们的代码
- ❌ "模型给的参数是一个字典" → ✅ 是一段 JSON 文本，要先解析，而且可能格式不对
- ❌ "工具出错就抛异常、让程序停下" → ✅ 把错误写成说明交回给模型，让它自己改正
- ❌ "说明书随便写一句就行，模型很聪明" → ✅ 模型只能靠说明书了解工具，写得含糊它就会用错
- ❌ "工具越多 Agent 越强" → ✅ 功能重叠的工具越多，模型越容易选错
