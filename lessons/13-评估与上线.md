# 第 13 课：评估与上线

> **学完你能**：说清楚为什么 Agent 不能凭「感觉还行」就上线；用测试题和评分程序给 Agent 打分；知道上线后要盯哪些指标、怎么省钱；做出你自己的毕业项目。

## 基础

### 1. 为什么要评估
- Agent 的回答**每次都不完全一样**。你改了一句 Prompt，可能这道题变好了，那道题却变差了。
- 只凭「我试了几次，感觉还行」是不够的。要准备一组**测试题**，每次改 Prompt、改工具、换模型后都跑一遍，用同一把尺子对比。
- 比喻：新菜上架前，要请一桌人按同一张评分表试吃，而不是厨师自己尝一口说「挺好」。

### 2. 几个术语（来自 Anthropic 的 Agent 评估文章）
- **task（测试题）**：一道题，包括输入和「怎样算做对」
- **trial（一次尝试）**：同一道题让 Agent 做一次。因为每次结果不一样，一道题常常要做好几次
- **grader（评分器）**：判断做没做对的那段逻辑
- **transcript（运行记录）**：Agent 这一次的完整过程：说了什么、调用了哪些工具、拿到什么结果
- **outcome（最终结果）**：看**环境里实际发生了什么**，而不是 Agent 嘴上说了什么。比如订机票的 Agent 说「已经帮你订好了」，要去数据库里看是不是真有这张订单

### 3. 三种评分方式
- **代码评分**：写程序检查。比如「回答里必须出现某几个字」「必须调用了某个工具」「文件里必须有某一行」。又快又便宜、结果稳定，能用就先用它
- **模型评分**（LLM-as-a-Judge）：让另一个大模型按评分标准打分。适合「讲得够不够简单」「有没有泄露答案」这种程序判断不了的事
- **人工评分**：人来看。最准但最慢，主要用来**校准模型评分**：抽一些题人工打分，看评委模型和人的判断是否一致
- 模型评分也会判错（Hugging Face 的课程在评分结果页就提醒学员这一点），所以评分标准要写具体，并让评委写出理由

### 4. 怎么起步
- 不用一开始就准备几百道题。Anthropic 的建议是**从 20~50 道题起步**，题目最好来自**真实的失败**：用户在哪里卡住、Agent 在哪里出错，就把它写成一道题
- **一定要读运行记录**。通过率只告诉你「错了多少」，运行记录才告诉你「为什么错」
- 如果某道题所有尝试都是 0 分，先怀疑题目本身：是不是要求写得不清楚、评分标准有问题

### 5. 看看本项目
在终端里运行 `agent-tutor --eval`，就会把 `evals/cases.json` 里的 16 道测试题自动跑一遍（摸底、接着上次的进度讲、出题不泄露答案、复习到期的错题、答错先给提示、检查作业、安全等）。每道题会：
1. 准备一份假的学习进度和一个临时练习目录（不会动你真正的进度和文件）
2. 让导师回答。评估时允许导师在临时目录里写文件、改文件、领取作业；运行命令、MCP 工具一律拒绝（`src/eval.ts` 里的 `ALLOWED`）
3. 用**代码评分**检查：有没有调用该用的工具（比如出题要派出题官）、有没有调用不该用的工具（比如被要求读 key 时不能运行命令）、文件改对了没有
4. 代码查不了的（「讲得是不是够简单」「有没有直接给答案」），交给**评委模型**按评分标准判断，就是模型评分。可以用环境变量 `JUDGE_MODEL` 换一个更强的评委
- 最后显示通过率和花费，详细报告（含导师每一轮的回答，也就是运行记录）存在 `~/.agent-tutor/evals/`。可以自己往 `cases.json` 里加题，用 `--only 名字` 只跑其中几道
- 动手作业的 `check.py` 也是代码评分：导入学生的代码，跑一组测试，输出每项通过没有、没通过的原因

### 6. 成本：token 就是钱
大模型按 token 收费。导师每说完一轮，下面那行灰字就是这一轮的用量，输入 `/cost` 看总账。要知道：
- **输入 token**：每调用一次模型，就要把整段对话重新发一遍，所以对话越长越贵；一轮里调用了几次工具，就要发几遍
- **缓存**：和上一次开头相同的内容，很多服务商按便宜得多的价格收费。所以 System Prompt 和工具说明尽量不要每轮都变（本项目 `src/usage.ts` 会统计命中缓存的部分）
- 省钱的办法：压缩对话（第 7 课「记忆与上下文工程」）、把查资料这种会读很多网页的事派给子 Agent（第 11 课「多 Agent 与框架」）、简单任务换便宜的小模型

### 7. 上线
- 做成别人能用的形态：本项目就是一个命令行工具，发布到 npm 后，别人 `npm install -g` 就能用；也可以做成网页、聊天机器人等
- 上线前的安全检查（API Key 怎么放、工具权限、危险操作先问人、护栏）在第 12 课「安全、护栏与人工介入」里讲
- 记录日志，观察真实用户在哪里卡住，持续改进

## 进阶

### 1. 两类评估：能力评估和回归评估（Anthropic）
- **能力评估**：考 Agent 还做不好的事。刚开始通过率低很正常，它的作用是指出改进方向
- **回归评估**：考 Agent 已经做好的事，通过率应该接近 100%。作用是防止「改好了 A，改坏了 B」
- 能力评估里的题做稳了，就挪进回归评估

### 2. pass@k 和 pass^k
同一道题做 k 次：
- **pass@k**：k 次里**至少成功一次**的概率。适合「多试几次、挑一个对的就行」的场景，比如生成几个方案让人挑
- **pass^k**：k 次**全部成功**的概率。适合「每次都必须对」的场景，比如客服 Agent 每个用户都只给一次机会
- 例子：单次成功率 75%，连续 3 次全成功的概率约 0.75³ ≈ 42%。看起来不错的 75%，放到要求每次都对的场景里，就远远不够

### 3. 错误分析和组件级评估（吴恩达《Agentic AI》第 4 模块）
- Agent 由很多环节组成：理解问题、选工具、填参数、读结果、写回答……整体分数低时，**先找出是哪个环节最该改**，不要凭感觉乱改
- 做法：读一批失败的运行记录，给每个失败标上「错在哪个环节」，统计哪个环节错得最多，就先改它
- 对单个环节可以单独做评估（组件级评估），比整体评估更快、更便宜，也更容易看出改动有没有用

### 4. 可观测性：上线后看得见 Agent 在干什么（Hugging Face 附加单元、微软课程第 10 课）
- **trace**：一次完整的任务；**span**：其中的一步（一次模型调用、一次工具调用、一次检索）。一个 trace 由很多 span 组成，像一棵树
- 标准是 **OpenTelemetry**，常见工具有 Langfuse、Arize 等
- 要盯的指标：**延迟**、**成本**、**出错率**、**用户反馈**（包括用户换个说法重问这种不明说的不满意）、准确率
- **线上和线下形成闭环**：线上发现的失败用例，补进离线测试集，下次改动前先跑它
- 本项目的 `/details` 和 Ctrl+O 能展开每一轮的完整过程，就是一个最简单的「看运行记录」

### 5. 降成本的工程做法
- 先用**最强的模型**把效果做出来、建立基线，再把各个环节**逐个换成小模型**，每换一个就跑一遍评估，确认效果还达标（OpenAI 的 Agent 搭建指南）
- **路由**：先判断问题难不难，简单的交给小模型（第 6 课「工作流与设计模式」里的路由模式）
- **缓存**：常见问题的答案缓存起来（微软课程第 10 课）；固定的 System Prompt 放在最前面，提高服务商的缓存命中率

## 常见误区
- ❌ "我试了几次感觉还行，可以上线了" → ✅ 要用一组固定的测试题，改动前后对比
- ❌ "Agent 说做完了，就是做完了" → ✅ 看 outcome：去环境里检查是不是真做完了
- ❌ "能用模型评分就都用模型评分" → ✅ 能用代码检查的先用代码，模型评分也会判错，要用人工抽查校准
- ❌ "通过率 0% 说明 Agent 太差" → ✅ 先检查题目和评分标准本身有没有问题
- ❌ "单次成功率 75% 挺高了" → ✅ 要求每次都对的场景看 pass^k，连续 3 次全对只有约 42%
- ❌ "上线就结束了" → ✅ 上线后要盯指标、读运行记录，把线上的失败补进测试集

## 动手作业（作业名：13-eval）
自己写一个迷你评估程序：跑一组测试题、用代码评分判断每道题对不对、算出通过率和失败清单。
进阶档还要算 pass@k 和 pass^k，并找出「改动前通过、改动后失败」的回归题。

## 毕业项目
用学到的知识，做一个**你自己的 Agent**：比如「记账助手」「英语陪练」「旅行规划师」。可以直接复制本项目来改。交付要求：
1. **System Prompt**：写清楚角色、要做什么、不能做什么，用标题或标签分好区（第 2 课「Prompt 怎么写」）
2. **至少 3 个工具**：说明书写清楚，出错时返回能让模型自己改正的说明（第 4 课「工具调用」）
3. **至少 10 道测试题**：其中至少 3 道是安全题（比如有人要它泄露隐私、执行危险操作），评分方式至少用到代码评分
4. **一份评估报告**：通过率、失败的题错在哪个环节、你改了什么、改完后的通过率；进阶档再加上同一道题跑 3 次的 pass^3
