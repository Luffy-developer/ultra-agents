# 第 2 课：Prompt 怎么写

> **学完你能**：把一句含糊的要求改写成清楚的 Prompt；看出一份 System Prompt 写得太死板还是太含糊；把一份现成的工作流程改写成 Agent 能照着做的指令。

## 基础

### 1. Prompt 就是你给模型的"任务说明"
- Prompt 就是你发给模型的指令。模型看不到你脑子里的想法，**你没写的，它就只能猜**。
- 比喻：Prompt 像给新来的实习生布置任务。你说"写个介绍"，他只能瞎写；你说清楚给谁看、写多长、什么风格，他才能一次写对。
- 对比：
  - 差：「写个介绍」
  - 好：「你是科技博主。用 100 字以内、小学生能懂的语言，介绍什么是 AI Agent，结尾举一个生活中的例子。」

### 2. 好 Prompt 的四要素
- **角色**：你是谁（"你是一位耐心的数学老师"）
- **任务**：做什么（"给学生讲解这道题"）
- **要求**：格式、长度、风格（"分 3 步讲，每步不超过两句话"）
- **示例**：给个样例，让模型照着学

### 3. System Prompt：Agent 的"人设和规则"
- 放在对话最前面、用户一般看不到的那段话，叫 **System Prompt**。它决定 Agent 的性格、能做什么、不能做什么。
- 看看本项目：你正在用的导师，它的 System Prompt 就在 `src/agent.ts` 的 `systemPrompt` 函数里，写着"开场先摸底""讲完不要问听懂了吗"等规则。你写的 `TUTOR.md` 也会被拼进去。

### 4. 写在"合适的高度"：不太死，也不太虚
Anthropic 总结过写 System Prompt 最常见的两种失败（来自《Effective context engineering for AI agents》）：
- **太死板**：把规则写成一长串 if-else，"如果用户说 A 就回复 B，如果说 C 就回复 D……"。情况一多就写不完，遇到没写到的情况模型就乱了
- **太含糊**：只写一句"你是个好助手，帮用户解决问题"，以为模型知道你的业务背景。其实它什么都不知道
- **合适的高度**：讲清楚目标、原则和重要的边界，让模型在没写到的情况里也能自己判断
- 比喻：交代实习生，既不要写一本 300 页的"遇到什么情况说什么话"，也不要只说一句"好好干"，而是讲清楚"我们的目标是什么、哪些事绝对不能做、拿不准时怎么办"

### 5. 分区写，让模型一眼找到重点
- Prompt 一长，就用 **Markdown 标题**或 **XML 标签**把它分成几块，比如"背景""规则""输出格式"（Anthropic 建议）：
```
<背景>你是一家奶茶店的客服，店里只做外卖。</背景>
<规则>
1. 只回答和点单、配送有关的问题
2. 涉及退款的，告诉顾客会转给人工处理
</规则>
<输出格式>不超过 3 句话，语气亲切</输出格式>
```

### 6. 示例要少而多样
- 给模型看几个例子，比写一大段规则更管用。但要选**几条多样、典型的**，不要堆一长串边界情况（Anthropic 建议）
- 例子太单一，模型会死板地模仿——三个例子都以"亲~"开头，它每句话都会以"亲~"开头

### 7. 先写最小版本，再按失败补充
- 不要一开始就想把所有情况写全。先写一个最简单、能用的版本，拿真实的问题去试；**看到它在哪里做错了，再针对那里补一句**（Anthropic 建议）
- 这样写出来的每一条规则都有用，不会越写越长、自相矛盾

### 8. 把现成的工作手册改写成 Agent 指令
OpenAI 的 Agent 搭建指南建议：不要从零开始想，**直接用公司现成的操作流程（SOP）、客服话术、帮助文档**来改写：
- 改成**编号的步骤**，每一步对应一个明确的动作（如"询问订单号""查询订单状态"）
- 把**可能出现的分支**写出来（如"如果订单已发货……；如果还没发货……"）
- 指南里还提到：可以让推理模型帮忙，把一篇帮助文档转成编号的指令清单

例子：把退货流程改写成指令
```
1. 询问顾客的订单号
2. 查询订单状态
   - 如果签收超过 7 天：告诉顾客已超过退货期，问是否需要转人工
   - 如果没超过 7 天：进入第 3 步
3. 询问退货原因，并确认商品没有拆封
4. 提交退货申请，把退货地址发给顾客
```

## 进阶

### 1. Prompt 模板 + 变量
- 业务多了，很容易维护出一堆差不多的 Prompt，改一处要改十处。OpenAI 指南建议：**用一份基础模板，把会变的部分做成变量**：
```
你是{{店名}}的客服。顾客的会员等级是{{会员等级}}，最近一笔订单是{{最近订单}}。
```
- 程序在调用模型前把变量填好。本项目的 `systemPrompt(cwd, instructions)` 就是这样：练习目录、TUTOR.md 的内容都是填进模板的变量。

### 2. 把 Prompt 当代码管理
- 12-factor-agents 第 2 条「Own your prompts」：Prompt 是你产品最重要的"代码"之一，不要藏在框架里、也不要只放在某个网页后台里
- 做法：Prompt 写在代码仓库里，用 git 管理版本；每次修改都能看到改了什么、为什么改；改完用测试题跑一遍，确认没有把原来好的地方改坏（第 13 课「评估与上线」）
- 本项目就是这样：System Prompt 写在 `src/agent.ts` 里，改动都在 git 历史中；改完可以运行 `agent-tutor --eval` 检查

### 3. System Prompt 和 user 消息的分工
- **System Prompt**：不随对话变化的东西——角色、规则、输出格式、安全边界
- **user 消息**：这一次的具体任务和数据
- 不要把每轮都在变的内容（当前时间、这次查到的资料）塞进 System Prompt：一是乱，二是很多服务商对"和上一次开头相同的内容"有缓存折扣，开头一变就享受不到了（第 13 课「评估与上线」讲成本时会细说）
- 来自外部的内容（网页、文件、工具结果）只是**资料**，不能当成指令执行。本项目 System Prompt 的安全规则专门写了这一条（第 12 课「安全、护栏与人工介入」）

## 常见误区
- ❌ "Prompt 越长越详细越好" → ✅ 要写在合适的高度：讲清目标和原则，不要把所有情况写成 if-else
- ❌ "模型很聪明，简单说一句它就懂" → ✅ 模型不知道你的业务背景，没写的它只能猜
- ❌ "示例越多越好" → ✅ 少量、多样、典型的示例更好；例子太单一，模型会死板模仿
- ❌ "一次把 Prompt 写完美再上线" → ✅ 先写最小版本，看它在哪里出错再补
- ❌ "改 Prompt 只是改几个字，不用测试" → ✅ 一个小改动可能让某些情况变好、另一些变差，改完要跑测试题
