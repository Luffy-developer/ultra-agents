# 第 14 课：生产级 Agent 工程

> **本课只有进阶档学，基础档可跳过。**
>
> **学完你能**：说出把 Agent 做成能长期稳定运行的产品要注意哪些工程原则；让 Agent 在等人回复时暂停、存档，之后接着跑；把「找人帮忙」和「高风险操作要审批」做成 Agent 循环里的正常步骤。

## 概览
前面 13 课做出来的 Agent，能在终端里陪你聊天、干活。但真要交给公司、给成千上万的用户用，会碰到新问题：
- Agent 要等经理审批退款，等了两个小时，程序总不能一直开着干等
- 服务器重启了，正在跑的任务不能从头再来
- Prompt 改坏了要能查出是哪次改的，能退回去

**12-factor-agents** 总结了 12 条原则来回答这些问题。核心观点是：**好的 Agent 大部分就是普通软件，只在关键位置嵌入大模型**。本课挑其中最有用的几条来讲。

## 进阶

### 1. 工具调用就是「结构化输出」（第 1、4 条）
- 第 1 条：**把自然语言转成工具调用**。用户说「给张三退 50 块」，模型的工作就是把它变成 `refund(user="张三", amount=50)` 这样一个结构化的指令
- 第 4 条：**工具就是结构化输出**。模型并不「执行」任何东西，它只是输出了一段格式固定的 JSON；接下来做什么，由你的代码决定（回顾第 4 课「工具调用」）
- 这样想的好处：你可以对这段 JSON 做任何处理——校验、改写、先存起来等人审批，而不一定马上执行

### 2. Prompt 和上下文都要自己掌握（第 2、3 条）
- 第 2 条 **Own your prompts**：Prompt 是代码，要放进版本管理，每次改动都能查到、能回退，改完跑评估（第 13 课「评估与上线」）。不要把它藏在某个框架的默认设置里，出了问题都不知道模型到底看到了什么
- 第 3 条 **Own your context window**：发给模型的内容用什么格式，由你决定。可以自己设计格式（比如把每个事件用 XML 标签包起来），让信息更紧凑；也可以在这一步过滤掉敏感数据
- 本项目：导师的 System Prompt 就写在 `src/agent.ts` 的 `systemPrompt` 函数里，和代码一起提交；对话太长时怎么压缩，也是自己写的（第 7 课「记忆与上下文工程」）

### 3. 用工具联系人类（第 7 条）
- Agent 需要人来回答、确认时，不要让它直接输出一段文字然后停下，而是给它一个工具 `request_human_input`，参数包括：
  - `question`：要问什么
  - `urgency`：有多急
  - `format`：希望人怎么回答，`free_text`（随便写）、`yes_no`（是或否）、`multiple_choice`（选择题）
- 好处：「问人」变成了和「查天气」一样的一次普通工具调用，可以统一记录、统一处理。人可以通过 Slack、邮件等任何渠道回复
- 这样一来，Agent 也不必只活在聊天窗口里：它可以由**定时任务（cron）或网络回调（webhook）触发**，在后台自己跑，需要人的时候再发消息找人

### 4. 启动、暂停、恢复（第 6 条）和控制流（第 8 条）
- 第 6 条：Agent 要能用简单的接口**启动、暂停、恢复**
- 第 8 条 **Own your control flow**：循环是你写的，所以可以在「模型选好工具」和「真正执行」之间插一步：
  - 模型调用了 `request_human_input`，或者调用了退款这类**高风险工具**
  - 你的代码把整段对话、以及还在等结果的那次调用的 `tool_call_id` **存下来**（存到数据库或文件），然后**退出循环**，不占着程序干等
  - 人回复了（比如通过 webhook 通知你），读出存档，把人的回复作为这次工具调用的结果放回对话，**接着跑**
- 状态要能**序列化**（比如转成 JSON 存下来）。这样服务器重启了，读出存档照样能继续
- 人拒绝了高风险操作怎么办？把「被拒绝」作为工具结果交回给模型，让它换个做法或向用户解释——拒绝也只是一种工具结果
- 本项目：写文件、运行命令前弹出的「允许吗？」就是这一步的简化版（程序在终端里等你按键，没有存档退出）；学生拒绝时，工具返回「学生拒绝了……请问问学生原因或换个做法」交回给模型（见 `src/tools.ts`）

### 5. 错误压缩进上下文（第 9 条）
- 工具出错时把错误整理好交回给模型，让它自己改；记录连续出错的次数，大约 3 次就停下来交给人（第 5 课「Agent 循环」的作业就是这个）

### 6. 小而专的 Agent（第 10 条）
- 一个 Agent 只负责一件明确的事，每次任务控制在 3~10 步，最多 20 步左右
- 步骤越多，上下文越长，模型越容易迷失。大任务拆给几个小 Agent，比一个什么都管的大 Agent 可靠（回顾第 11 课「多 Agent 与框架」）

### 7. 无状态的 reducer（第 12 条）
- 原文这一条只有标题「Make your agent a stateless reducer」，没有展开
- 可以这样理解：把 Agent 的一步看成一个函数，输入「目前的状态 + 新发生的事件」，输出「新的状态」，函数本身不偷偷记任何东西。所有的状态都在你存下来的那份记录里，所以才能随时暂停、恢复

### 8. 框架里的做法：LangGraph 的人工介入
LangChain Academy 的 LangGraph 课程有一整个模块讲人工介入，提供了现成的工程实现：
- **断点**：在图的某个节点前停下，等人看过再继续
- **编辑状态**：人可以在暂停时直接修改 Agent 的状态（比如改掉一个填错的参数），再让它继续
- **时间回溯**：回到之前某一步的状态，从那里重新跑
- 这几个功能的前提，都是「状态被完整保存下来」——和上面第 6、12 条是同一个道理

### 9. 跨会话的长任务（回顾第 7 课）
Anthropic 做长任务的经验（详见第 7 课「记忆与上下文工程」）：先列一份 JSON 格式的功能清单；每个会话只做一个功能，结束时提交 git、更新进度文件；新会话开始先读进度和 git log。
这也是「状态存在外面、Agent 每次读出来接着干」的做法。

## 常见误区
- ❌ "Agent 等人回复时，就让程序开着一直等" → ✅ 把状态存下来、退出循环，人回复了再恢复
- ❌ "状态放在内存里就行" → ✅ 状态要能序列化存起来，程序重启了照样能接着跑
- ❌ "问人就是让模型输出一句话然后停下" → ✅ 做成 `request_human_input` 工具，问人也是一次普通的工具调用
- ❌ "人拒绝了操作，Agent 就该报错退出" → ✅ 把「被拒绝」作为工具结果交回给模型，让它换个做法
- ❌ "用了框架就不用管 Prompt 和上下文" → ✅ 要清楚模型每一步实际看到了什么，Prompt 要放进版本管理
- ❌ "一个 Agent 包揽所有事最省事" → ✅ 小而专的 Agent 更可靠，大任务拆开做

## 动手作业（作业名：14-human-in-loop）
用假的大模型写一个会「暂停等人」的 Agent：模型调用 `request_human_input` 时，把状态存成一个字典并返回「等待中」；人回复后，用 `resume` 接着跑完。
进阶要求：状态经过 JSON 存取之后照样能恢复（模拟程序重启）；退款这类高风险工具执行前也要暂停等审批，人拒绝时把「被拒绝」交回给模型。
