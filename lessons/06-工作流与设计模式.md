# 第 6 课：工作流与设计模式

> **学完你能**：分清「工作流」和「Agent」；遇到一个需求，说出该用哪种模式、为什么；知道什么时候根本不该用 Agent；亲手写出提示链、路由和「边写边改」的循环。

## 基础

### 1. 工作流 vs Agent：谁来决定下一步
上一课的 Agent 循环里，**下一步做什么由模型自己决定**。但很多任务的步骤是固定的，用不着让模型去想。Anthropic 把这两种做法分开叫：
- **工作流（Workflow）**：步骤由**我们的代码**事先定好，模型只负责其中某几步。比如"先写文案 → 再翻译"，顺序写死在代码里
- **Agent**：步骤由**模型**在运行时自己决定，调用什么工具、做几步，事先不知道

比喻：工作流像**流水线**，每个工位做什么是定好的；Agent 像**请来的师傅**，你只说要什么，他自己安排怎么干。

**能简单就简单**：Anthropic 的建议是先用最简单的办法——很多时候一次模型调用、加上检索和几个例子就够了。确实不够，再上工作流；工作流还不够，才上 Agent。越往后越灵活，但也越慢、越贵、越难预测。

### 2. 五种常用的工作流模式（来自 Anthropic《Building effective agents》）

**① 提示链（Prompt chaining）**：把任务拆成几步，前一步的输出交给后一步，中间可以加**检查关卡**
- 生活例子：写一封英文推荐信——先用中文列要点，检查要点齐不齐，齐了再写成英文
- 适合：任务能清楚地拆成固定的几步。每一步更简单，所以更准；代价是要多调用几次模型
- 检查关卡可以是普通代码（字数够不够、有没有某个关键词），不合格就不进下一步

**② 路由（Routing）**：先判断问题属于哪一类，再交给对应的处理流程
- 生活例子：医院的分诊台，先问清症状，再告诉你去内科还是外科
- 适合：问题类型差别很大、分开处理效果更好的情况。比如客服里"退款""技术问题""一般咨询"各走各的流程；简单问题交给便宜的小模型，难题交给强模型
- 一定要有**默认分支**：分类结果不认识时，也要有地方去

**③ 并行（Parallelization）**：几件事同时做，最后汇总。分两种：
- **分段**：把任务拆成互不相关的几块，同时做。例子：一份报告的三个章节同时写
- **投票**：同一件事做好几遍，比较结果。例子：检查一段代码有没有漏洞，让三个模型各看一遍，有一个说有就重点查
- 适合：子任务互不依赖，可以省时间；或者需要多个视角来提高把握

**④ 编排者-工作者（Orchestrator-workers）**：一个"总指挥"模型根据具体任务**临时**决定拆成哪几块，派给"工人"去做，最后汇总
- 生活例子：装修队的工头，看了房子才决定要找水电工、木工还是油漆工
- 和"并行"的区别：并行的分工是事先定好的；这里的分工要看到任务才知道
- 适合：事先没法确定要做哪几步的复杂任务，比如改代码时要改几个文件，得看了需求才知道

**⑤ 评估者-优化者（Evaluator-optimizer）**：一个模型写，另一个模型（或同一个模型换个角色）按标准挑毛病，写的人根据意见改，循环几轮
- 生活例子：写作文——你写初稿，老师批改，你按批注改，直到老师满意
- 适合：评价标准清楚，而且"按意见改"确实能改好的任务，比如翻译、写文案
- 一定要设**最多改几轮**，否则可能一直改不完

### 3. 什么时候不该用 Agent
OpenAI 的 Agent 搭建指南给了三条标准，**至少符合一条**才值得考虑做 Agent：
- **复杂的判断**：要根据具体情况灵活拿主意，比如判断一笔退款申请合不合理
- **规则多到难以维护**：用 if-else 写的规则已经又多又乱，改一条就出问题
- **大量非结构化数据**：要读懂邮件、文档、聊天记录这类自然语言

反过来：规则清楚、步骤固定的任务（比如"每天把表格里的数据汇总发邮件"），写普通代码就好，又快又便宜又稳定。

### 4. 三条设计原则（来自 Anthropic）
- **简单**：能用简单的就别用复杂的
- **透明**：让人看得到 Agent 在计划什么、做了哪些步骤（本项目的「⎿ [todo]待办清单」和工具调用提示就是为了透明）
- **认真打磨 Agent 和工具之间的接口**：工具的说明书、参数、返回的错误信息，都要像给人设计界面一样用心（第 4 课「工具调用」讲过）

## 进阶

### 1. 吴恩达的四大 Agent 设计模式
DeepLearning.AI 的《Agentic AI》课程把 Agent 的设计归成四种模式：
- **反思（Reflection）**：让模型检查、批评自己（或别人）的输出，再改进——就是上面的评估者-优化者
- **工具使用（Tool use）**：让模型调用搜索、代码执行等工具（第 4 课「工具调用」）
- **规划（Planning）**：让模型先把任务拆成步骤，再一步步执行
- **多 Agent（Multi-agent）**：几个分工不同的 Agent 协作（第 11 课「多 Agent 与框架」）

这门课还专门讲了评估和错误分析：先找出整条流程里哪个环节最拖后腿，再集中改那个环节（第 13 课「评估与上线」）。

### 2. 看看本项目：出题官 + 审题官 = 评估者-优化者
- 打开 `src/subagents.ts`：出题官 `quiz-maker` 设了 `reviewer: "quiz-reviewer"`，出完题会自动交给审题官检查
- 审题官第一行写「结论：通过」或「结论：不通过」，不通过就把意见带回去让出题官改
- `MAX_REVISIONS = 2`：最多退回改 2 次，还不通过就交给导师自己判断——这就是"最多改几轮"
- 注意审题官的标准写得很具体（考的是不是讲义里的、提示有没有泄露答案……）。**评估标准越清楚，这个模式越有效**

### 3. 结构化规划：先出计划，再执行，结果出来再调整
（参考微软 AI Agents for Beginners 第 7 课「规划」）
- 让模型输出**结构化**的计划，而不是一段自由文字。比如用 Pydantic 定义"子任务列表"，每个子任务写清楚做什么、交给哪个 Agent，代码就能按计划逐个派发
- 计划不是一成不变的：某一步的结果出来后（比如查到航班已满），把结果交回给模型，让它**重新规划**剩下的步骤
- 本项目的 `todo_write` 是一个轻量版：计划是一份待办清单，导师边做边更新（第 5 课「Agent 循环」）

### 4. 元认知：Agent 反思自己是怎么想的
（参考微软 AI Agents for Beginners 第 9 课「元认知」）
- 元认知就是"对自己的思考进行思考"：Agent 根据过去的经验，评估并调整**自己的做法**，而不只是改一次输出
- 微软课程列出的几个方面：自我反思（找出自己哪里做得不好）、自我评估（检查推理和决策，比如发现"太依赖用户上次的偏好了"）、调整策略、自己发现并改正错误、合理安排时间和算力
- 例子：旅行助手推荐过一家已经订满的酒店，以后推荐前就先严格检查有没有空房；按"最便宜"推荐用户不满意，就改成按"质量最好"推荐
- 和反思模式的区别：反思是改**这一次的结果**；元认知是改**以后的做法**

### 5. 怎么选模式：从简单往复杂试
1. 一次模型调用能不能搞定？能就别加
2. 步骤固定 → 提示链；类型分明 → 路由；可以同时做 → 并行；有明确的评价标准 → 评估者-优化者
3. 步骤事先定不下来 → 编排者-工作者，或者干脆用 Agent
4. 这些模式可以组合：路由之后的某个分支里，再套一个提示链

## 常见误区
- ❌ "Agent 比工作流高级，能用 Agent 就用 Agent" → ✅ 步骤固定的任务用工作流更快、更便宜、更稳定；Agent 是不得已才用的
- ❌ "路由只要把几类问题分对就行" → ✅ 一定要有默认分支，模型给出意料之外的分类时程序不能卡住
- ❌ "提示链就是多调用几次模型" → ✅ 关键是中间的检查关卡：上一步不合格就不往下走，错误不会一路传下去
- ❌ "评估者-优化者会一直改到完美" → ✅ 必须设最大轮数；评价标准不清楚时，改多少轮都不会更好
- ❌ "并行就是编排者-工作者" → ✅ 并行的分工事先定好；编排者是看到任务后临时决定怎么分

## 动手作业（作业名：06-workflow）
用一个按剧本回复的假大模型，写出两种工作流：带检查关卡的提示链（文案不合格就不去翻译），以及带默认分支的路由（先分类，再交给对应的处理函数）。
进阶档还要写一个评估者-优化者循环：写 → 评 → 按意见改，评估通过或改到最大轮数就停。
