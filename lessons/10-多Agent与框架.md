# 第 10 课：多 Agent 与框架

## 核心概念
- **多 Agent**：一个 Agent 什么都干容易乱，可以拆成多个分工明确的 Agent 协作。
  例如：「出题 Agent」负责出题，「批改 Agent」负责判分，「导师 Agent」负责统筹。
- 常见协作方式：
  - **流水线**：A 做完交给 B，B 做完交给 C
  - **主管模式**：一个主管 Agent 把任务分派给几个专家 Agent，再汇总结果
- 实现上很简单：**把另一个 Agent 包装成一个工具**，让主 Agent 去调用它。

## 比喻
一个人开餐馆：既当厨师又当服务员又收银，忙不过来还容易出错；
多 Agent = 招几个人分工，店长负责协调。

## 看看本项目
导师就是一个「主 Agent」，它有一个特别的工具 `task`，专门用来派**子 Agent**干活（和 Claude Code 的做法一样）。
打开 agent-tutor 源码里的 `src/subagents.ts`：
- 每个子 Agent 有**自己的人设**和**自己的 messages**，看不到你和导师的聊天记录，所以导师派活时要把任务写清楚
- 每个子 Agent **只能用分配给它的工具**：出题官只能读讲义，调研员只能上网，谁都不能再派子 Agent（防止无限套娃）
- 子 Agent 自己跑一遍完整的 Agent 循环（就是第 5 课的 `runTurn`），做完**只把结论交回给导师**，
  中间搜到的十几个网页不会塞进导师的对话里——这是拆分子 Agent 最大的好处：**隔离上下文**
- 导师在同一步里派出好几个子 Agent，它们会**同时开工**，比一个一个来快
- 终端里出现「⎿ [agent]… 派出子 Agent」，下面缩进一层的 ⎿ 行就是子 Agent 在用的工具

内置了三个子 Agent：出题官 `quiz-maker`、调研员 `researcher`、通用助手 `general-purpose`。
输入 `/agents` 查看；你还可以在 `~/.agent-tutor/agents/` 里写一个 Markdown 文件，定义自己的子 Agent：

```markdown
---
name: code-reviewer
description: 代码检查员：检查学生写的代码有没有错误
tools: read_file, list_files
---
你是代码检查员。先用 list_files 找到文件，再用 read_file 读代码，逐个指出问题。
```

`description` 很重要：导师就是看它来决定什么时候派这个子 Agent 的（和工具说明的作用一样）。

## 什么时候该拆子 Agent
- 适合：任务独立、步骤多、过程不重要只要结果（查资料、跑通一段代码、检查一批文件）
- 不适合：简单的一两步小事（派活本身也要花时间和 token），或者需要和学生来回商量的事

## 框架
- 常见框架：LangChain / LangGraph、LlamaIndex、AutoGen、CrewAI、OpenAI Agents SDK 等。
- 框架帮你封装好了 Agent 循环、记忆、RAG 等"轮子"，写起来更快。
- 建议：**先像本项目一样手写一遍原理，再用框架**。这样框架出问题时你知道去哪里查。

## 反思：让另一个 Agent 帮你检查
人写完东西会检查一遍，Agent 也可以：**一个负责做，另一个负责挑毛病，不合格就退回去改**。这叫**反思**（Reflection）。
- 本项目的出题官出完题，会自动交给「审题官」`quiz-reviewer` 检查：题目讲义里讲过吗？答案对吗？提示有没有把答案说漏？
- 审题官第一行写「结论：通过」或「结论：不通过」，不通过就把意见交回给出题官修改，**最多改 2 次**（防止一直改不完）
- 终端里会看到「⎿ [agent]quiz-reviewer：不通过，退回修改」，然后出题官再交一版
- 你自定义的子 Agent 也能用：在文件开头加一行 `reviewer: 审核员的名字`
- 为什么要另一个 Agent 来审？自己检查自己，容易"看不出自己的错"；换一个只负责挑错的人设，更容易发现问题

## 小测验
问：怎样让一个 Agent "调用"另一个 Agent？
答：把另一个 Agent 包装成一个工具函数（输入任务、返回结果），注册到主 Agent 的 tools 里。
